### B2. The refusal gate fails open on missing or misrouted `industry`. HIGH
`buildFundamentalsPayload.ts:95` and `:127-133`. This is the refusal-gate rule inverted: an unknown classification
must refuse, not proceed. Measured through the real builder (all with shares and positive FCF present):

| Input | Result |
|---|---|
| no `summaryProfile`, no `assetProfile` | **DCF runs** |
| `summaryProfile` present, no `industry` key | **DCF runs** |
| `summaryProfile: {}` and `assetProfile.industry = 'Banks - Regional'` | **DCF runs** (a bank) |
| `assetProfile` only, `Banks - Regional` | refused |
| `industry` not a string | **DCF runs** |

Cause: `profile = summaryProfile || assetProfile` (`:95`) takes the first truthy object, and `{}` is truthy, so a
populated `assetProfile` is hidden. Then `typeof profile?.industry === 'string' ? ... : ''` turns "unknown" into `''`,
which matches nothing. The template's `${industry || 'this business'}` (`:132`) is dead code: `''` can never reach it,
which shows the empty case was considered and then not handled.

Fix: read field by field, `summaryProfile?.industry ?? assetProfile?.industry` and
`summaryProfile?.sector ?? assetProfile?.sector`. If industry is absent, fall back to `sector === 'Financial Services'`
(refuse) and otherwise, if both are absent, refuse with "classification unavailable". `industryKey`/`sectorKey` are
also typed on both profile interfaces (`quoteSummary-iface.d.ts:50-56`, `:760-770`) and are slug forms that do not
carry the display-string punctuation. Delete the dead `|| 'this business'`.
Tests: absent profile, profile with no industry, `{}` plus populated `assetProfile`, non-string industry.

## Answers to the five questions

### Q1. Is FCFE the correct reading of this cash flow? UNVERIFIED
What I checked in `node_modules/yahoo-finance2` 3.13.2:
- `esm/src/modules/quoteSummary-iface.d.ts:312` declares `freeCashflow?: number;` on `FinancialData`, with no doc comment.
  `:313` declares `operatingCashflow?: number;`. Neither carries a definition.
- A case-insensitive search for `levered` and `unlevered` across the whole package (ts, js, md) returns **zero** hits.
- The `CashflowStatement` interface in the same file (`:118-122`) holds only `maxAge`, `endDate`, `netIncome`. So the
  statement-level fallbacks in `pickFcf0` (`:61`, `:63-64`) read fields the library does not type, and by the PR's own
  measurement the module is emptied. The fallback is dead in production; `fcf0` is `financialData.freeCashflow` or null.
- The only places the repo says "levered" are the PR text and the author's own memory note
  (`vendor_shape_lessons_quantan.md`), which records the claim without a source. That is not evidence from a permitted source.

So "Yahoo labels it levered" is a hypothesis about a vendor field, not a finding. Three further points hold **even if
the levered reading is right**:
1. Levered FCF is not Damodaran's FCFE. FCFE = CFO - capex + net borrowing (ch. 14). A vendor levered FCF typically omits net
   borrowing. Using it as a perpetuity makes this "FCFE assuming zero net borrowing", a modelling assumption that should be
   named, not an identity.
2. Whether the figure deducts principal repayment, stock-based compensation, minority-interest share or preferred dividends
   is unknown. The platform has no SBC detail and no minority/preferred data, so the equity value attributable to common
   holders cannot be bridged.
3. Direction of the risk: if the field is in fact unlevered, removing the bridge **raises** the equity value of every
   levered name by roughly net debt. The error flatters, so it is the direction to re-measure first.

Proposed owner probe (field presence only, I8-safe, no vendor values committed): for 4 to 6 levered names compare
`financialData.freeCashflow` with `financialData.operatingCashflow` and with trailing FCF, interest paid and capex from
`fundamentalsTimeSeries`. If it tracks CFO less capex it is an after-interest (US GAAP) statement FCF and the FCFE
reading is defensible as an approximation. Until then the on-screen wording must stay hedged (B4).

### Q2. Is the remaining model internally consistent? Arithmetic yes; construction no
Arithmetic, `dcf.ts:60-69` and `:79`: end-of-year discounting of five grown cash flows, Gordon terminal on year-5 FCF x (1+g),
discounted at `(1+r)^5`, equity / shares. Internally consistent. Per-share division is correct if `fcf0` and `shares`
are in the same absolute units and the same currency (see S7 for the currency gap).

Terminal-value share (`pvTerminal / enterpriseValue`), which the DCF discipline says to report every time. It depends only
on rates and growth, not on fcf0 or shares, so these are the production splits for every name that gets a DCF at the
defaults (9%, tg 2.5%, growth 2/5/9%): **bear 67%, base 75%, bull 79%**. The UI renders none of them
(`ValuationTab.tsx:63-92` shows only `valuePerShare`). The fixture's own split is 74.9%.

Scenario deltas, `buildFundamentalsPayload.ts:141`, `:155` (all measured through `runDcf`, FCF 100, 10 shares):

| Input rate | Bear / base / bull rates | Bear / base / bull value per share | Ordering |
|---|---|---|---|
| 4.0% | 5.5 / 4.0 / **6.0** | 291 / 768 / 391 | **bull below base** |
| 5.0% | 6.5 / 5.0 / **6.0** | 227 / 460 / 391 | **bull below base** |
| 6.0% | 7.5 / 6.0 / **6.0** | 185 / 328 / 391 | bull rate equals base rate |
| 7.0% | 8.5 / 7.0 / **6.0** | 157 / 255 / 391 | ordered; bull delta is exactly -1.0pp (floor boundary) |
| 9.0% (default) | 10.5 / 9.0 / 8.0 | 120 / 176 / 247 | ordered |

The bull floor is an absolute 6% (`Math.max(q.wacc - 0.01, 0.06)`), not relative to the base rate or the terminal growth.
For every input rate from 4.0% to 7.0% the bull rate is pinned at 6.0% and the bull value is 391 whatever the slider says
(measured at 4.0, 5.0, 5.5, 6.0, 6.5, 7.0). The row label "Bull (lower discount rate, higher growth)" (`ValuationTab.tsx:85`,
relabelled by this PR) is false at an input rate of 6.0% (equal) and below it (the bull rate is *higher*); it is true at 6.5%
(lower by 0.5pp) and at 7.0% the delta is exactly the intended 1.0pp, which is the boundary of the `max(., 0.06)` floor. The bear
row label (`:73`) is never false on the rate (bear is always +1.5pp); "lower growth" is false only if the growth inputs are out
of order. The slider allows 4% (`:43`, route clamp `route.ts:55`). Growth ordering is also not enforced: gBear 12% / gBull 0% returns
bear 180 > base 176 > bull 167. The magic numbers 0.015, 0.01, 0.06, 0.02 have no names or citations (HOUSE STYLE).

"Cost of equity 9% with terminal growth up to 6%": that exact corner is unreachable. `runDcf` accepts tg up to 6%
(`dcf.ts:57`) but the route clamps tg to 5% (`route.ts:56`) and the slider to 4.5% (`ValuationTab.tsx:44`). The singularity
is guarded only as `wacc <= tg -> null` (`dcf.ts:56`); there is no minimum spread, so the value diverges as the spread
closes. Reachable by URL, measured: wacc 6.0%/tg 5% gives 1,050 per share (TV 95%), wacc 5.1%/tg 5% gives 10,500 (TV 99.5%),
wacc 5.01%/tg 5% gives 105,000 (TV 100%), against a 10 per-share cash flow. At the defaults with tg 5% the base is 83% terminal.
From the slider alone: wacc 5.0%, tg 4.5% gives 2,140 base against a 227 bear (9.4x), TV 98%. So the model is bounded away from
division by zero but not meaningful near it, and nothing flags it. A 5% terminal growth also exceeds a long-run nominal
growth / risk-free ceiling (Damodaran: g <= rf), which is the usual cap and is not stated anywhere.

### Q5. Does anything here make the buy/sell-zone surface worse? Yes for refused names, neutral elsewhere
- Refused names: the composite becomes the midpoint of price and analyst target (or the target alone), the signal and score
  change (B1 table), and the Summary panel does not say a DCF was refused (B5). The methodology string still names DCF.
- Non-refused names: no numeric change. But the relabel to "cost of equity" gives the flat 9% an authority it did not have
  as a "WACC". For a levered company the cost of equity exceeds WACC, so a 9% default that was a plausible WACC is
  low as a cost of equity, and the DCF anchor (and hence the buy ceiling) is biased upward for exactly the names the
  FCFE label invites you to treat as levered. Beta is already in the payload (`market.beta`, `:235`) and unused (S6).
- Pre-existing and unchanged: the forward-heuristic anchor is approximately the price (circular), so even a three-anchor
  median is pulled toward the current price. Route to the backlog, not this PR.
