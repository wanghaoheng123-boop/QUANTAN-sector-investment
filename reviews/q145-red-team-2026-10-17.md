### Q145-R3 · MEDIUM · the Bloomberg producer still fabricates 0, and it outranks Yahoo's real change

`lib/data/bloomberg/bridgeClient.ts:183-189`, `lib/data/mergeQuotes.ts:127-129`.

The bridge does `change = pickNumber(...) ?? 0`, and the same for `changePct`,
`volume` and `pe`. In the merge, Bloomberg's `change`/`changePct` always win
(`change: bb.change`). Reproducer (tsx, `fetch` stubbed to return a bridge row
`{symbol:'SPY', last:500}` with no change; Yahoo row has change 5 / 1.02%):

```
bridge row (no change supplied): {"change":0,"changePct":0,"volume":0,"pe":0}
merged (Yahoo had a real change): {"price":500,"change":0,"changePct":0,"src":"bloomberg","prov":"bloomberg"}
```

This is exactly the defect Q-145 exists to remove: a measured-looking "0.00%"
FLAT, and here it **overwrites** a real vendor change and attributes it to
Bloomberg in `provenance`. The new `UnifiedQuote` docstring
(`lib/data/mergeQuotes.ts:31-37`) says "every other number may be null and
renders '—'". On this path that is false. It is latent: it needs
`BLOOMBERG_BRIDGE_URL` and `BLOOMBERG_REDISTRIBUTION_ACK`. If enabled, it
also feeds a fabricated `prev.change = 0` into `resolveTickChange`, which then
derives `tick.price − prev.price` and labels it the session change.

**Fix:** have `BloombergQuoteNormalized.change/changePct/volume/high52w/low52w/pe`
be `number | null`. In the merge, use `bb.change ?? y.change` with per-field
provenance (the file's own comment, `mergeQuotes.ts:87-89`, already describes
this tightening). Add a merge test with a bridge row that omits change.

### Q145-R4 · MEDIUM · "same New York session" is a calendar-date check, and that is wrong for 24h instruments

`lib/quoteChange.ts:24-30,44`.

`sameNySession` compares `nyDateYmd` of the two stamps. For US equities that
is sufficient. `regularMarketTime` is a regular-session time, and a NY calendar
day holds at most one regular session. I probed the NY-midnight edge and both
DST transitions, and they behave correctly (see TRUE list). But `/stock/[ticker]`
accepts any symbol, so `/stock/btc-usd` and `/stock/cl=f` reach the same merge,
and those instruments roll their reference close at a different time:

```
BTC prev 19:30 EDT, tick 20:30 EDT (crosses 00:00Z)   {"change":5,"changePct":5}
CL=F prev 16:30 ET, tick 18:30 ET (new globex session) {"change":2,"changePct":2.8169…}
```

Yahoo's crypto day rolls at 00:00 UTC (20:00 EDT / 19:00 EST). CME energy rolls
at 18:00 ET. In both cases the "prior close" is stale and the derived number is
a two-session move labelled as today's.

**How a tick gets there.** The interval tick cannot cross those boundaries,
because the single-ticker route's interval skips its fetch outside NYSE hours
(`app/api/stream/[ticker]/route.ts:214`, `if (!open) return`). The route does
emit an initial quote on **every connection**, with no market-hours check
(`:165-187`). The server soft-closes before `STREAM_MAX_DURATION_S = 300`,
and `useLiveQuote` reconnects on `close` / `closing_soon`
(`hooks/useLiveQuote.ts:212-239`). So a page left open emits one tick every few
minutes all night. Concrete sequence:
1. Open `/stock/btc-usd` at 19:55 EDT. The REST `prev` carries the change
   measured from the 00:00Z close of the old UTC day.
2. A reconnect at 20:02 EDT returns an initial quote with no change.
3. Both stamps fall on the same NY date, so the function derives
   `tick.price − old prior close` and shows it as today's move.

It only fires when Yahoo omits both change fields, which is rare. But the
docstring and commit claim "session", and the code checks the date.

**Fix:** restrict the derivation to instruments whose session is the NYSE
regular session (e.g. pass `calendar: 'us-equity'` from the caller, and return
null otherwise), or rename the check and say so. Add BTC and futures cases to
`quoteChange.test.tsx`.

### Q145-R6 · LOW · `resolveTickChange` passes impossible or inconsistent values through

`lib/quoteChange.ts:33-42`.

```
changePct -150, change null          → {"change":null,"changePct":-150}
change >= price (priorClose<=0)      → {"change":6,"changePct":null}
inconsistent pair (+5 / −3%)          → {"change":5,"changePct":-3}
prev = other ticker (250/+2), tick 1  → {"change":-247,"changePct":-99.597}
```

- A percent at or below −100 implies a non-positive prior close. It is returned
  as-is, and the stock and sector headers render `▼ — (150.00%)`.
- When `change >= price` the change is kept but the percent is dropped. The
  header then shows "— (no change data)" even though a change is known.
- `ChangeLike` carries no ticker, so nothing in the function stops a cross-ticker
  `prev`. The callers key correctly today (the landing page by map key; the
  stock and sector pages remount per param), so this is a latent API hazard.

**Fix:** return null for both fields when `changePct <= -100` or the implied
prior close is `<= 0`. Add `ticker` to `ChangeLike` and return null on a
mismatch.

### Q145-R7 · LOW · two percent formulas for the same inputs

`lib/yahooQuoteFields.ts:31` vs `lib/quoteChange.ts:37-38`.

`normalizedChangePercent` computes `implied = 100·change/price`, which uses the
current price as the denominator. `resolveTickChange` uses
`change/(price − change)`, the prior close, which is correct.

```
normalizedChangePercent(null, 10, 110)  → 9.0909
resolveTickChange change 10 price 110   → {"change":10,"changePct":10}
```

When Yahoo omits the percent, `/api/prices` and both streams serve 9.09%,
while the client derivation would say 10%. The parity fixture encodes the same
error: `DECIMAL_FORM_ROW` calls change 1.6 at price 100 "a true +1.6% move",
but that move is 1.626%. The error is small for normal moves and has been there
since before this PR. This PR adds a third route through the normaliser and a
second formula beside it.

**Fix:** `implied = 100·change/(price − change)` with a `> 0` guard, and correct
the fixture comment.

### Q145-R8 · LOW · "missing" means different things on different surfaces

- `app/desk/page.tsx:223` requires **both** `change` and `changePct`, so it
  discards a known percent when only the absolute change is missing. Every
  other surface shows the percent.
- `app/page.tsx:219,365,395`: a sector with a price but no change has no
  session move, so it is counted as "No quote" while its card shows a price.
- `app/api/stream/route.ts:139-141` accepts `price <= 0` (finite only), while
  `/api/prices` and the single stream require `> 0`. `parseLiveQuote` drops it
  client-side, so the harm is caught one layer down.

**Fix:** one shared predicate for "has change", and say "no change data"
rather than "No quote" when there is a price.
